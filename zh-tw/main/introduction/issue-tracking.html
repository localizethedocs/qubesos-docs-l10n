議題追蹤

我們使用 GitHub 議題作為我們的議題追蹤系統。所有與 Qubes OS 專案相關的議題（包括本網站等輔助基礎設施）都在 qubes-issues 中追蹤。

如何開啟新議題

首先，讓我們確認議題追蹤器是正確的地方。

我需要協助、有問題，或想討論某事。

我們很樂意提供協助、回答問題和進行討論，但議題追蹤器不是進行這些活動的合適場所。請參閱協助、支援、郵件列表與論壇。

我看到文件中有應該修改的內容。

我們鼓勵您自行提交變更！請參閱 :doc:`如何編輯文件 </developer/general/how-to-edit-the-rst-documentation>`了解操作方法。如果是您無法自行處理的事項，請繼續開啟議題。

我想回報安全性漏洞。

謝謝您！如果漏洞是機密的，請不要在我們的公開議題追蹤器中回報。請參閱在 Qubes OS 中回報安全性問題。

我仍然想開啟議題。

太好了！感謝您花費時間和精力協助改善 Qubes！為確保流程對所有參與者高效且富有成效，請遵循以下步驟：

  1. 仔細閱讀我們的議題追蹤指南。如果您的議題會違反任何指南，請停止。請不要提交。

  2. 搜尋現有議題，包括已開啟和已關閉的，檢視您的議題是否已存在。如果已存在，請停止。:ref:`不要開啟重複的議題。<introduction/issue-tracking:new issues should not be duplicates of existing issues>`請改為在現有議題上留言。

  3. 前往此處。

  4. 選擇您要開啟的議題類型。

  5. 輸入描述性的題名。

  6. 不要刪除提供的議題模板。填寫所有適用的區段。

  7. 請注意，AI 經常會對 Qubes OS 產生幻覺。如果您正在使用 AI 協助，請將其結論與`官方文件 <https://doc.qubes-os.org/>`__ 進行比對。

  8. 確保提及您已經看過的任何相關文件和其他議題。除非您告訴我們，否則我們不知道您看過什麼。如果您沒有列出，我們會假設您沒有看過。

  9. 如果議題模板的任何區段*確實*不適用，您可以移除它們。

  10. 提交你的議題。

  11. 回覆官方團隊提出的任何問題。例如，您可能會被要求提供特定的日誌或其他附加資訊。

最終，您的議題可能會被關閉。請參閱 議題如何被關閉 了解何時、為何以及如何發生的詳細資訊。

議題的組織方式

議題可以具有多種不同的屬性，並以各種方式組織。本節說明我們如何使用標籤、議題類型、專案以及 GitHub 議題追蹤系統的其他功能，以保持 qubes-issues 有條不紊。

標籤

當議題首次建立時，它會自動獲得 ``P: default``（即預設優先權）`標籤 <https://github.com/QubesOS/qubes-issues/labels>`__。在議題建立後，只有 Qubes 團隊成員有權限修改標籤。許多標籤上都有說明，可透過懸停滑鼠或查看`標籤列表 <https://github.com/QubesOS/qubes-issues/labels>`__ 來檢視。讓我們來看一些最重要的標籤。

優先權

有幾個議題優先權等級，從 P: minor 到 ``P: blocker``（完整列表請參閱`此處 <https://github.com/QubesOS/qubes-issues/labels?q=P%3A>`__）。每個開啟的議題應該只有一個優先權。開啟的議題不應有多個優先權，也不應完全缺乏優先權。請參閱此處了解開發者如何使用這些優先權的詳細資訊。

組件

有許多組件標籤，每個都以 C: 開頭（完整列表請參閱`此處 <https://github.com/QubesOS/qubes-issues/labels?q=C%3A>`__）。每個開啟的議題應至少有一個組件。開啟的議題可以有多個組件，但不應完全缺乏組件。當沒有其他適用的組件時，請使用 C: other。

受影響的版本

格式為 affects-<RELEASE_NUMBER> 的標籤表示議題影響相應的 Qubes OS 版本。如果議題影響多個版本，它可以有多個此類標籤。

類型

議題有三種`類型 <https://docs.github.com/en/issues/tracking-your-work-with-issues/configuring-issues/managing-issue-types-in-an-organization>`__：Bug、Feature 和 Task。

  • Bug — 意外的問題或行為

  • Feature — 請求、想法或新功能

  • Task — 特定的工作項目

每個開啟的議題應只有一種類型。Bug 回報針對已經存在的事物中的問題。如果某物還不存在，但您認為它應該存在，那麼該議題應該是 Feature 請求。如果某物已經存在，但您認為它可以在某些方面改進，那也屬於 Feature 請求。Task 類型適用於可執行的議題，但不屬於 Bug 或 Feature 類型。

專案

根據 GitHub，專案 是「一個可調適的試算表、任務板和路線圖，與您的 GitHub 議題和拉取請求整合，協助您有效地規劃和追蹤工作。」議題追蹤器有幾個`專案 <https://github.com/QubesOS/qubes-issues/projects>`__。GitHub 專案允許更詳細的議題狀態，以及為議題附加更多中繼資料。它們也允許更聚焦的檢視。

Qubes OS 專案中有一個特殊專案：Current team tasks 專案，它代表了核心團隊目前的工作。此專案待辦事項區段中的議題尚未準備好進行工作——它們可能正在等待說明、阻礙排除、優先權決定等。已準備就緒的議題可由任何團隊成員接手。已準備就緒欄中不應有太多議題，以減少混淆和決策癱瘓——理想的數量約為 20 個。審查中狀態表示開發者已完成工作（已達到完成狀態）——如果某些事項必須推遲或放棄，應在議題討論中發布理由。

元議題

元議題是一個主要用於收集和組織其他議題群組的議題。這組其他議題通常存在於`子議題 <https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues>`__ 的階層中，通常元議題位於頂層。（例如，當我們需要追蹤特定功能的工作時，我們使用元議題。我們不能使用 專案 來達成此目的，因為我們已經使用專案來追蹤整個 Qubes 團隊的工作，而專案不能包含里程碑或其他專案。）

元議題應有資訊豐富的說明，而不僅僅是議題列表。特別是，每個元議題應說明其目標、涵蓋範圍，以及相關的分類和優先權。

此外，元議題應有關於何時關閉的明確、具體且可執行的標準。元議題不應是「開放式的」或預期會無限期保持開啟。如果這點變得不明確，則應關閉元議題，直到情況明朗為止。

搜尋技巧

  • 錯誤的回報可能是已關閉的。此時，檢視`所有錯誤回報（包括已開啟和已關閉，按最近更新排序）<https://github.com/QubesOS/qubes-issues/issues?q=sort%3Aupdated-desc%20type%3ABug>`__會很有幫助。

  • 使用標籤搜尋。 例如，您可以按優先權（blocker、critical、major 等）和按組件（core、manager/widget、Xen 等）來搜尋議題。

  • 按關閉原因搜尋：reason:completed 和 reason:"not planned"。

  • 按專案搜尋。

指南

議題追蹤器不是討論論壇

議題追蹤器是一個幫助開發者提高工作效率的工具。它不是討論的地方。如果您想在議題追蹤器中討論某事，請在論壇或郵件列表中進行（請參閱協助、支援、郵件列表與論壇）。您可以在討論文章中直接連結到相關議題。

這項指南對於保持議題聚焦於*可操作的資訊*非常重要，這有助於開發者保持專注於他們的工作。當開發者回來處理一個議題時，我們不希望他們在開始之前必須篩選大量不必要的評論。在很多情況下，一個變得「太大」的議題本質上就變得麻煩多過其價值，沒有開發者會去碰它（另請參閱 每個議題必須關於單一、可操作的事項）。在這些情況下，我們有時不得不關閉議題並開啟一個新的。這對所有參與者來說都是浪費精力，因此我們請求大家幫助避免重複這種模式。

不要提交問題

qubes-issues 不是提問的地方。這包括但不限於疑難排解問題和關於如何使用 Qubes 的問題。請參閱 協助、支援、郵件列表與論壇 尋找適合提問的地方。相對地，qubes-issues 旨在追蹤影響廣泛 Qubes 使用者的更一般性的錯誤、增強功能和任務。

使用議題範本

當您開啟新議題時，會為您提供一個議題範本。請使用它。不要刪除它。議題範本經過精心設計，以獲取重要資訊。沒有這些資訊，議題很可能不完整。（如果某些部分不適用，您可以移除它們，但請謹慎使用，且僅在它們*確實*不適用時才這麼做。）

同樣重要的是注意議題範本中 HTML 註解的位置和內容。這些有助於我們保持議題格式的一致性。

每個議題必須關於單一、可操作的事項

如果您的議題不可操作，請參閱 協助、支援、郵件列表與論壇 尋找適合發布的地方。如果您的議題涉及多個事項，請分別提交為單獨的議題。這意味著我們通常不應嘗試將單一議題用作僅為分組、包含或追蹤其他議題而存在的「元」或「史詩」議題。相反地，當需要將多個相關議題分組時，請使用`專案 <https://github.com/QubesOS/qubes-issues/projects>`__。

這項指南對於使議題追蹤器成為開發者的有用工具極為重要。當議題過於龐大且複雜時，它會變得難以處理，並大幅增加什麼都無法完成的機率。此類議題也往往會鼓勵過多的一般性討論，這根本不適合技術性議題追蹤器（請參閱 議題追蹤器不是討論論壇）。

每個議題必須是單一類型

每個議題必須是以下類型中的剛好一種：錯誤回報（bug）、功能或改進請求（enhancement），或任務（task）。不要提交多種類型的議題。請改為提交多個不同類型的議題。Qubes 團隊將根據其類型對您的議題進行分類。

新議題不應是現有議題的重複

在提交議題之前，請檢查它是否已被回報過。在**篩選器**方塊中輸入關鍵字，搜尋現有議題——包括已開啟和已關閉的。如果您找到似乎與您相似的議題，請仔細閱讀。

對於錯誤回報，如果您找到與您相同或包含您問題的議題，請在現有錯誤回報議題上留言，而不是開啟新的，即使現有錯誤回報已關閉（除非現有議題是很久以前修復的）。如果錯誤回報影響多個受支援的 Qubes 版本，我們通常只為所有目前受支援的版本保留一個錯誤回報。如果錯誤回報因所有受影響版本已達生命週期終點而關閉，而您在目前受支援的版本上遇到相同的錯誤，請留言告知。

對於功能請求，如果初始實作不完整或不成功，請在現有功能請求議題上留言。但是，如果功能的初始實作成功，而您回報的是後來出現的功能問題，請開啟單獨的錯誤回報，而不是在舊的功能請求上留言。

每當您在議題上留言時，Qubes 團隊將會看到您的留言並對該議題採取適當的行動。例如，您可以留下包含附加資訊的留言，以幫助維護者除錯問題。新增留言將使您訂閱電子郵件通知，這有助於獲取有關議題的重要更新。如果您沒有什麼要補充但仍想接收電子郵件更新，您可以按一下議題上的「訂閱」按鈕。

新議題應包含所有相關資訊

當您提交新議題時，應確保包含您使用的 Qubes 版本以及相關軟體套件的版本（如何從 dom0 複製資訊）。如果您的議題與硬體相關，請提供盡可能多的硬體詳細資訊。一個很好的方法是 產生並提交硬體相容性列表（HCL）報告，然後在您的議題中連結到它。您可能還需要使用 lspci 等命令列工具。如果您回報的錯誤位於 測試 儲存庫中的套件，請在 updates-status 儲存庫中引用相應的議題。專案維護者非常感謝詳盡的說明。這通常有助於他們更快地解決問題，所以每個人都受益！

不保證您的議題會得到處理

請記住，qubes-issues 是一個議題追蹤器，不是支援系統。建立新議題只是您提交項目供 Qubes 團隊考慮的一種方式。由 Qubes 團隊決定是否或如何處理您的議題，這可能包括在未採取任何行動的情況下關閉議題。然而，即使您的議題保持開啟，您也不應期望它在任何特定時間範圍內得到處理，或根本不會被處理。在撰寫本文時，qubes-issues 中有遠遠超過一千個開啟的議題。Qubes 團隊有自己的路線圖和優先權，這將決定開啟議題的處理方式和順序。

議題和留言必須以英文撰寫

如果英文不是您的母語，您可以發布機器翻譯。如果您願意，也可以在 可折疊區段 中包含原始的非英文文字。

開發者可能會要求您提供日誌或其他資料

在某些情況下，處理議題的 Qubes 開發者可能會向您請求日誌或其他資料。Qubes OS 從不會*自動發送此類資料，您*從不需要*提供它。但是，如果沒有日誌，開發者可能無法診斷和修復您遇到的錯誤。*如果您願意，您*可以*提供此類資料，例如在相關議題的留言中發布。

在某些情況下，一位 Qubes 開發者可能開始處理一個議題，然後另一位開發者可能在之後接手。如果您將日誌或其他資料發送給第一位開發者，第二位開發者也將需要存取該資料。因此，透過與 Qubes 團隊成員分享資料，您即授予他們與 Qubes 團隊其他成員分享該資料的權限。

請**不要**向開發者發送未經請求的通訊，或試圖直接聯繫他們尋求協助。

對冗長、非必要的內容使用可折疊區段

在 GitHub 上，按如下方式在 Markdown 中建立可折疊區段：

<details>
<summary>Summary goes here. This line is optional.</summary>

Long, nonessential content goes here. You can put a code block here, but make sure to leave empty lines before and after the fence lines (```).

</details>

提示： 在發布前使用「預覽」標籤頁確保其正確顯示。

議題如何被關閉

如果 Qubes 開發者進行了解決議題的程式碼變更，該議題通常會從相關的提交或已合併的拉取請求（PR）中關閉。

臭蟲回報

對於錯誤，包含變更的套件將移至適當的測試儲存庫，然後再移至適當的穩定儲存庫。如果您願意，您可以在測試儲存庫中測試修復，或者等待它進入穩定儲存庫。

解決方案

在 GitHub 中，議題可以「已完成」或「不計劃」的方式關閉。

以 completed 關閉表示議題已修復（對於錯誤）或已完成（對於增強功能和任務）。更精確地說，這表示包含相關工作的提交已推送。

以 not planned 關閉表示該議題*不會*被修復（對於錯誤）或完成（對於增強功能和任務）。當議題以 not planned 關閉時，我們會新增一個以 R: 開頭的**解決方案**標籤，指定關閉的原因。

雖然以 not planned 關閉的議題會獲得更具體的解決方案標籤，但以 completed 關閉的議題不一定會獲得一個，因為連結的 PR、提交、自動化訊息和 completed 原因本身通常足以傳達所有相關資訊。

向後移植

GitHub 中的議題只能開啟或關閉，但對於影響多個 Qubes OS 版本的錯誤，有幾種可能的狀態：

  1. 尚未修復

  2. 修復已開發但尚未提交（PR 已開啟）

  3. 修復已提交（PR 已合併），但更新尚未推送至任何儲存庫

  4. 更新已推送至最新開發版本的測試儲存庫

  5. 更新已推送至最新開發版本的穩定儲存庫

  6. 更新已向後移植至穩定版本並推送至測試儲存庫

  7. 更新已推送至穩定版本的穩定儲存庫

我們在第 3 步關閉議題。然後，隨著更新的發布，議題會自動獲得適當的 current-testing 和 stable 標籤。

因此，如果您看到一個議題已關閉，但修復尚未提供給您，請注意它可能處於此過程的中間階段，介於議題關閉和更新在您使用的 Qubes 版本中可用的儲存庫之間。

為了協助解決此問題，我們有一個名為 backport pending 的標籤，表示「修復已針對測試版本發布，但正在等待向後移植到穩定版本。」

理解已開啟與已關閉的議題

每個議題總是處於兩種狀態之一：開啟或關閉，其中開啟是預設值。**開啟**和**關閉**狀態意味著，根據我們目前可用的資訊，該議題*是*或*不是*（分別）可供 Qubes 團隊操作的。

工作流程與議題狀態的含義

我們在指派議題和為其加上標籤時使用一些規則。

指派議題

為避免議題「死亡」的情況（指派給沒有積極處理的人），並幫助團隊組織工作，議題應指派給目前正在處理它的人，或在不久的將來（大約一到兩週）將開始處理它的人。

議題不應作為未來幾個月的待辦事項列表進行指派，也不應在未經對方明確確認目前正在處理或即將開始處理的情況下指派給某人。

處理議題

每個議題應包含明確的成功陳述：議題何時完成？對於提出議題的人來說可能不清楚，但在開始工作之前，處理議題的人應確保描述中包含明確的完成標準。

如果議題需要超過一到兩天的時間，也應有大約的時間估計。當然，這可能在之後更新。

當議題完成時（即完成檢查清單已全部完成），該議題應移至 Current team tasks 專案中的 ready 欄。
